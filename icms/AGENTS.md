# ICMS / Contrlio 项目协作规则

## 项目唯一事实源

本仓库是项目需求、实现、已确认决策和任务状态的唯一事实源。ChatGPT Project、Work、Codex 中的讨论结论，必须写入仓库对应文档后，才作为后续任务依据。不要把某一次聊天历史作为唯一依据。

业务运行记录以 PostgreSQL 为准，上传文件以 MinIO 为准；本规则不代表聊天记录、数据库或上传文件会自动同步到 GitHub。

## 开始任务前必读

按以下顺序阅读，再检查本次涉及的代码和专项文档：

1. `docs/PROJECT_CONTEXT.md`：项目目标、技术栈、实际状态、关键入口。
2. `docs/REQUIREMENTS.md`：业务要求、COSO 内控闭环和实现边界。
3. `docs/ARCHITECTURE.md`：实际模块、数据流与部署方式。
4. `docs/DECISIONS.md`：已确认决策和待确认项。
5. `docs/TASKS.md`：已完成、进行中、下一步和阻塞项。

`README.md` 保留启动说明；`docs/PRODUCT_REQUIREMENTS.md`、`DOMAIN_MODEL.md`、`ERD.md`、`RBAC.md` 及功能专项文档提供细节。文档与源码冲突时，核对代码和配置，修正文档，并在决策/任务记录中说明；不得凭空补成已实现功能。

## 改动与交接

- 保留现有目录与业务数据。避免与任务无关的重构、覆盖和删除；文档任务只改文档。
- 开始和结束时检查 Git 根目录、分支、状态和 remote；保留已有改动。当前 Git 根目录位于 `icms` 的上一级，使用前重新确认。
- 已保存本地项目入口也在上一级；父级 `AGENTS.md` 负责转入本工程规则。保留父级仓库范围，不建立嵌套仓库；交接方式见 `docs/PROJECT_HANDOFF.md`。
- 按用户授权处理提交和推送；未经明确授权不要 push。不要自行移动 `.git`、初始化嵌套仓库或改 remote。
- 需求变化更新 `REQUIREMENTS.md`；架构/数据/部署变化更新 `ARCHITECTURE.md`；确认的取舍更新 `DECISIONS.md`；任务状态更新 `TASKS.md`。
- 记录完成证据：实际修改文件、验证方式与结果、未验证项。区分“源码已有实现”“本地验证通过”“生产发布完成”。
- 不把代码存在、历史说明或 `/health` 成功等同于业务闭环验收。生产发布应核对部署版本和所请求的具体功能。

## 实现约束

- 所有公司业务数据遵守服务端组织隔离和 RBAC；风险、控制、RCM 等关联须校验公司与流程边界。
- 证据使用真实 MinIO 对象和 PostgreSQL 元数据；行业模板不能生成虚假的执行结果、证据或整改完成状态。
- Issue 使用显式整改状态机，保留提交版本、复核和重测历史；不得通过普通编辑绕过状态和独立性校验。
- 流程配置当前是设计、草稿与版本发布能力。不要宣称发布后已启动业务审批、待办或通知引擎。
- AI 为可选能力。公司凭据加密保存，制度正文外传前逐次确认；法规索引不等于实时法律核验。
- `.env`、`.env.production`、访问令牌、密码、生产凭据及业务上传文件不写进文档或 Git。日常停止基础设施保留数据卷，删卷属于破坏性操作。
- 本地开发使用 `docker-compose.yml`；生产使用 `compose.production.yml` 与独立环境配置。不要将本地数据库或密钥自动复制到生产。

## 两种模式共同使用的方法

Work 和 Codex 应访问同一个 `icms` 目录。ChatGPT 中确认的需求与决策由可访问该目录的任务写入上述文档；Codex 开发后回写状态和变更。不同设备或工作区通过已配置的 Git 远端交换经审核的代码与文档。没有本地目录访问权限时，提供这些文档的最新副本，并标明版本。
