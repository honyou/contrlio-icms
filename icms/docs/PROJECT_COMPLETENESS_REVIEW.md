## 后续产品和工程优化

1. **账号与组织管理**：支持角色更新、密码变更/重置、已有账号重新加入公司；维护部门负责人和上下级。当前成员只有新增/移除，页面提示修改密码但没有对应功能。
2. **可追溯业务记录**：整改每轮保存根因、措施、期限的不可变快照；法规与公司流程关联落数据库并记录版本。当前整改 Submission 保存摘要/证据，旧计划内容会随重提变化；法规关联只存在页面内存。
3. **列表与导航**：加入服务端分页、业务筛选、关联跳转、URL 路由与直达链接。当前最多返回 500 条、无分页；菜单仅靠本地 state，刷新或浏览器后退无法保留工作位置。
4. **工作台准确性**：显示真实连接状态、逾期问题及责任人待办，移除无事实依据的“控制有效”固定提示；统计根据刷新策略更新并标明时间。当前统计数真实，但连接和有效性文案不代表实时检测结果。
5. **业务报告**：先做当前公司的风险清单、RCM、检查结果和整改报告导出；行业手册导出不能代替业务报告。
6. **AI 成果落地**：可选保存公司范围对话/草案，支持把经用户确认的建议转成整改计划；法规更新增加官方来源、核对日期、版本对比和人工确认。模型调用应保持可选、自有 Token。
7. **本地启动可复现**：增加 doctor/verify-local、健康等待和统一应用启动/停止脚本；MinIO 增加健康检查并锁定版本，使用锁文件安装。当前 MinIO 使用 latest，README 尚不能证明新电脑得到相同环境。
8. **文档和版本管理**：同步 README、ROADMAP、RBAC 与 AI 配置位置；固定历史迁移内容，避免初始迁移从未来版本的模型动态生成表；建立可追溯提交基线。目前 Git 状态显示 icms/ 整目录仍为未跟踪。

## 建议实施顺序与验收门槛

**第一轮：修复正确性和权限。** 编辑完整值、关联名称、真实默认值、证据上传反馈、成员权限撤销、检查状态、输入/日期/层级校验必须先完成。每个修复增加针对实际失败模式的回归验证。

**第二轮：完成真实本地闭环。** 使用独立验收公司和经理、责任人、审计员三类账号，在 PostgreSQL/Redis/MinIO 上走完：创建公司/部门/流程/风险/目标/控制/RCM → 上传证据 → 失败检查/Finding → Issue → 整改计划/证据 → 独立复核 → 重测 → Close → 核对 Dashboard 差值。验收包含浏览器操作、真实文件字节下载和 SHA-256、重启后数据保留。

同时必须验证：跨公司访问拒绝、Viewer 写入拒绝、移除成员/停用公司后所有整改写入拒绝、自审/自测/违规关闭拒绝、缺证据拒绝提交、旧轮次不能关闭新轮次、Finding 并发转换最多一次、数据库/对象存储失败回滚。

**第三轮：完善日常使用。** 请求竞态、操作权限一致性、每页指南、账号组织管理、分页/筛选、路由、报表与审计历史可见性。

**第四轮：扩展后续业务。** 结构化抽样和 Walkthrough，再到审计项目/调查与 AI 草案落地。保持本地开发路径，PHASE 12 通过后再进入生产部署。
