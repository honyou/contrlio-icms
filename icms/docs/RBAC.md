系统管理员拥有跨公司管理能力；公司经理创建公司时自动成为新公司的经理成员。公司“删除”采用可恢复停用：立即撤销该公司的业务访问，但保留业务行、Evidence 对象和审计记录；原公司的经理或系统管理员可恢复。一般业务授权按 membership.role 执行，而非仅看全局管理员状态。整改责任人须是当前启用公司的成员。

登录页的本地注册要求有效的一次性系统管理员邀请码，并在同一事务内新建独立用户、公司和经理 membership；只允许用户给自己创建首家公司，不提供任意账号接管或跨组织注册。邀请码由系统管理员签发，可撤销未使用的邀请码；数据库只保存摘要。既有账号登录不经过注册接口，继续使用原账号和公司关系。已加入任一启用公司的经理可以创建后续公司。行业参考目录对登录用户开放浏览，只有公司经理可向组织写入模板记录。

## 强制规则

1. 组织范围在认证依赖中解析，不接受前端传入的角色声明或 organization_id 作为授权凭证。
2. 每个列表查询、详情检索、变更、文件下载和 Dashboard 查询都先限定用户可访问的启用组织；公司停用/恢复另由该公司经理或系统管理员授权。
3. 创建关系时逐个加载外键目标并检查组织、流程的所有权；返回 404 或 403，不泄漏其他公司是否存在该 ID。
4. API schema 对各端点逐一允许字段。Issue 的普通更新不含状态字段；状态操作是独立路由。
5. 对证据下载再次鉴权业务关联目标；MinIO bucket 不公开，API 才能代理下载。
6. 经理和审计员不得复核/重测/关闭自己负责的整改。系统管理员也必须遵循职责分离。
7. 用户禁用、公司停用后即时拒绝新业务请求；公司停用保留资料以便恢复，撤销成员关系后不允许访问其业务文件。
8. 所有关键状态变化与 AuditEvent 同事务提交，普通用户不能修改/删除审计历史。
9. 制度分析仅经理/审计员可访问；API 逐次要求 `confirm_external_transfer=true` 后才将制度全文发送给 AI 服务商，上传本身不触发模型调用。

## 认证

密码采用合适的慢哈希。浏览器使用 HttpOnly JWT cookie、精确 localhost CORS、SameSite=Lax 与写操作 Origin 校验；API 文档工具可用 OAuth2 password/login 返回 Bearer token。登出撤销 JWT ID 并清理 cookie。Bootstrap 管理员由本地环境变量创建，命令可安全重复运行。

## 必须保留的拒绝验收

- 公司 A 用户无法猜测 UUID 读取/修改公司 B 的记录或下载证据。
- Viewer 写入返回 403。
- 其他人的责任人无法编辑或提交整改。
- 责任人无法复核、重测或关闭自己的 Issue，包括 system admin 作为整改责任人时。
- 缺整改证据不能提交；未通过复核不能重测；未通过重测不能关闭。
- 被冻结的计划和已提交 Evidence 不可修改；失败重提后旧版复核/重测不能使新版关闭。
- 同一个 Finding 并发转 Issue 最多成功一次。
