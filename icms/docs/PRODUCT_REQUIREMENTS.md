# 产品需求

本文保留第一版功能验收条目。2026-10-04 更新了邀请码注册要求；[业务需求与实现边界](REQUIREMENTS.md) 记录 COSO 闭环、后续扩展及尚未实现的目标/制度生命周期；任务完成状态见 [TASKS](TASKS.md)。

## 产品定位

ICMS 是面向企业内控团队的本地优先管理系统。第一版在个人电脑上启动，业务记录落 PostgreSQL，上传文件落 MinIO。页面必须调用真实 API；不得使用 mock 数据替代业务记录。

## 第一版使用角色

- 系统管理员：初始化系统，创建公司、组织成员和权限。
- 公司经理：维护本公司的部门、流程、风险、目标、控制、RCM，分配整改责任人并管理问题关闭。
- 内控审计员：执行检查，记录发现，转换问题，独立复核和重测。
- 整改责任人：维护本人整改计划、上传整改证据并提交复核。
- 只读查看者：查看授权公司内业务与 Dashboard。

公司成员通过 membership 关联公司与公司角色。所有业务列表、详情、写入和文件下载按当前登录用户的组织成员关系授权。

## 核心工作流程

新用户可在提供有效的一次性系统管理员邀请码后注册公司经理账号并建立公司工作空间；既有账号继续正常登录，无需邀请码。系统管理员也可替客户建公司。创建时可跳过行业样例，或选择行业和实践阶段生成可编辑的初始组织、流程、风险、控制、RCM 和待执行检查计划。用户可在行业参考库预览来源、组织结构、抽样建议和 Finding 到关闭的示例流程。之后在流程下完善风险、控制目标和控制措施，再建立 RCM。上传与 RCM 关联的设计或运行证据。审计员创建内控检查，检查具体 RCM 并记录结果；对失败项创建 Finding，再由该 Finding 唯一转换为 Issue。经理为 Issue 指定整改责任人、到期日和计划。责任人上传实际文件证据并提交一个带版本的整改修订。独立审计员复核通过、执行重测并记录结果，经理/审计员在通过重测后关闭 Issue。Dashboard 由 PostgreSQL 聚合这些记录。

## 功能需求

| 编号 | 功能 | 验收要点 |
|---|---|---|
| F-01 | 本地启动 | `docker compose up -d` 可启动 PostgreSQL、Redis、MinIO；Web 3000，API 8000，Swagger `/docs`，MinIO Console 9001。 |
| F-02 | 本地登录 | Bootstrap 账户使用 `.env` 的管理员邮箱和密码初始化；密码哈希存储；没有硬编码的生产凭据。 |
| F-03 | RBAC | API 对角色和公司成员关系授权；只读角色不可写；错误角色不能靠直连 API 越权。 |
| F-04 | 公司与部门 | 公司、部门及其状态保存在 PostgreSQL；部门属于一个公司。 |
| F-05 | 流程与风险 | 流程属于公司和部门；风险属于流程，保存描述及固有/剩余风险评估。 |
| F-06 | 控制目标与措施 | 控制目标和控制措施属于流程；保存所有者、频率与执行方式。 |
| F-07 | RCM | 每项 RCM 连接同公司、同流程的一个风险和一个控制；可浏览、创建、编辑。 |
| F-08 | Evidence | 文件字节写入 MinIO；元数据与 SHA-256 写入 PostgreSQL；下载校验公司范围；文件不得只登记文件名。 |
| F-09 | Inspection | 检查任务及其 RCM 检查项、执行人、结论、备注落库；失败项可生成 Finding。 |
| F-10 | Finding/Issue | Finding 关联检查项并分级；同一 Finding 只能创建一个 Issue。 |
| F-11 | Remediation | Issue 可分配责任人、整改计划和截止日；提交生成不可变版本；需当前版本有整改证据。 |
| F-12 | 复核、重测、关闭 | 复核人/重测人不能是责任人；不通过退回整改；仅当前版本通过复核和重测后可关闭。 |
| F-13 | Dashboard | 后端以所选公司范围对数据库真实聚合，显示 RCM 覆盖、检查结果、开放/关闭 Issue 和逾期整改。 |
| F-14 | 审计事件 | 登录后的关键写入、状态迁移记录 actor、动作、业务对象、时间及前后差异。 |
| F-15 | 邀请码公司自助注册 | 新注册必须提供系统管理员创建的有效邀请码；每码一次性使用，可撤销未用邀请码。邀请码与用户、公司、经理 membership 在一个事务中核验/创建，数据库仅保存邀请码摘要；密码哈希保存，可选行业模板初始化。已存在的账号及其登录不受影响。 |
| F-16 | 行业内控参考库 | 提供行业、实践阶段、组织结构、流程风险控制、抽样建议、证据类型及工作流样例；选用后生成可编辑的公司记录并留存审计事件；禁止伪造实际测试、MinIO Evidence 或整改完成结果。 |
| F-17 | 公司制度库与单份 AI 审阅 | 公司经理/内控审计员可上传 PDF、DOCX、TXT、Markdown 制度原件；文件存 MinIO，提取正文不落数据库；选择单份制度，经逐次确认后调用公司设置中当前配置的 AI 模型，结合行业法规索引生成可追溯风险与整改建议，结果、来源及 Token 用量落 PostgreSQL。 |
| F-18 | 制度/流程交叉 AI 分析 | 公司经理/内控审计员可选择至少两份公司制度和当前业务流程配置，逐次确认后调用公司配置的 AI，识别制度间、制度与流程间及流程间的直接冲突、执行口径差异、重复规定和责任/交接断点；报告提供来源摘录、影响、统一口径建议、来源哈希/流程版本及 Token 用量。范围与单次输入上限须在页面可见；不保存所提交的完整制度正文。 |

## Issue 生命周期

```text
open → in_progress → in_review → verified → retested → closed
                    ↑     ↓拒绝       ↓重测失败
                    └─────┴────────────┘
```

创建整改计划进入 `in_progress`。责任人提交一轮整改后进入 `in_review`，本轮整改资料冻结。通过复核转 `verified`，通过重测转 `retested`，之后方可关闭。复核或重测失败进入 `in_progress`，原提交、证据和意见均保留。普通 Issue 编辑不得修改状态。

## 非功能需求

- 优先兼容 Apple Silicon macOS；数据库、缓存和对象存储本地运行。
- FastAPI JSON API 提供 `/api` 路径和 Swagger 文档。
- UI 为中文第一版，可用浏览器完成建档、关联、状态流转和文件上传下载。
- 所有列表和图表均显示真实 API 数据、加载状态和错误信息；空状态可引导创建记录。
- 组织隔离是服务端规则。业务 UUID 不构成授权凭证。
- AI 配置可空；未配置时核心业务保持正常。
- 制度分析使用本地维护的官方来源法规索引摘要；用户可选粘贴官方法规摘录及 HTTPS `.gov.cn` 来源地址，不自动抓取法规全文或宣称实时核验；每条 AI 法规引用必须解析到系统已知法规 ID 和官方链接。
- 制度正文发送到第三方 AI 前必须逐次取得明确确认；扫描版 PDF 暂不支持 OCR，超过 60,000 字的文件须按制度/章节拆分，不能静默截断。
- 交叉分析只对当次选择的数据负责；总输入上限 100,000 字符，至少选择 2 份制度，最多 20 份制度、100 个活动流程。AI 结论不得直接修改制度或发布流程，必须人工确认。
- 行业模板应注明公开来源和司法辖区边界；阶段是控制实践路径，不应宣称为行业调查或强制标准。样本数量只作计划参考。
